# v0.1.0 Task Context Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make kernel tasks own their saved execution context and kernel-stack metadata, then prove that a real `Scheduler::Switch` drives two task round trips while the existing Ring 3/syscall path remains green.

**Architecture:** Keep x86_64 register manipulation in `crates/arch`, task ownership/state in `crates/kernel::task`, scheduling policy in `crates/kernel::scheduler`, and unsafe switch execution in the kernel runtime boundary. A `Task` will stop being `Copy`, own an architecture context plus optional kernel-stack metadata, and expose narrow accessors. The runtime will allocate a worker stack, install its prepared context into a real task, let scheduler decisions select the `from` and `to` task contexts, and execute those decisions cooperatively on real PIT-driven policy ticks. This slice does not claim interrupt-driven preemption.

**Tech Stack:** Rust `no_std`, x86_64 saved contexts, existing 4 KiB `FrameAllocator`, PIT 100 Hz, QEMU/OVMF, GitHub Actions.

**Spec:** `docs/roadmap.md` (`v0.1.0` context switching, kernel-stack lifecycle, repeatable scheduling)

## Global Constraints

- Safe Rust remains the default; raw register switching stays in `crates/arch`.
- `Task` owns context/stack metadata; scheduler policy must not duplicate execution state.
- Do not call the cooperative `context::switch()` directly from IRQ0; that would save the interrupt-handler call stack rather than the interrupted task frame.
- Use the existing physical-frame allocator and direct physical mapping; do not introduce a second allocator or a VM subsystem.
- Keep the existing Ring 3 -> `int 0x80` -> kernel -> Ring 3 -> `int3` smoke path green.
- Runtime evidence must distinguish timer-driven scheduling policy from true interrupt-driven preemption.

### Task 2: Turn scheduler decisions into prepared real switches

**Files:**
- Modify: `crates/kernel/src/scheduler.rs`
- Test: scheduler unit tests in the same file.

**Interfaces:**
- Produces: `pub struct PreparedContextSwitch { current: *mut Context, next: Context }`
- Produces: `Scheduler::prepare_context_switch(decision: ScheduleDecision) -> Result<PreparedContextSwitch, TaskTableError>`

The prepared switch is only valid for `ScheduleDecision::Switch { from, to }`. It copies the target context and returns a raw pointer to the source context so the temporary `&mut Scheduler` borrow ends before `context::switch()` suspends execution.

- [ ] **Step 1: Write failing scheduler/context integration test**

Create two tasks, install distinct context stack-pointer values, force a one-tick quantum, obtain `Switch { from, to }`, prepare it, and verify the copied target stack pointer matches the second task while the source pointer refers to the first task's stored context.

- [ ] **Step 2: Run CI and verify RED**

Expected: compile failure because `PreparedContextSwitch`/`prepare_context_switch` do not exist.

- [ ] **Step 3: Implement minimal switch preparation**

Resolve the task IDs from the decision through the owned `TaskTable`, copy `to`'s `Context`, take a raw pointer to `from`'s context, and return both without executing architecture-specific assembly in the scheduler.

- [ ] **Step 4: Re-run CI and verify GREEN**

Expected: all host tests pass and existing target build remains green.

### Task 3: Prove two scheduler-driven task round trips on real PIT policy ticks

**Files:**
- Modify: `crates/kernel/src/lib.rs`
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: `Scheduler::on_tick()` and `Scheduler::prepare_context_switch()`
- Consumes: `nastalli_arch::context::switch()`
- Produces runtime markers:
  - `Task switch: worker entered.`
  - `Task switch: bootstrap resumed.`
  - `Task switch: worker resumed.`
  - `Task switch: bootstrap resumed twice.`

- [ ] **Step 1: Add failing QEMU assertions for all four task-switch markers**

Keep the existing cooperative-context and Ring 3 assertions until the replacement path is proven.

- [ ] **Step 2: Run CI and verify RED**

Expected: static checks remain green and QEMU smoke fails on the first missing `Task switch:` marker.

- [ ] **Step 3: Build a real worker task**

Allocate one physical frame, reserve a small worker-state header at its bottom, use the remaining bytes as the worker kernel stack, call `context::prepare`, create a second `Task`, and install its context plus `KernelStack` metadata before constructing the scheduler.

- [ ] **Step 4: Drive policy from observed PIT ticks**

Add a helper that remembers the last observed PIT tick, calls `scheduler.on_tick()` once for each newly observed tick, and returns only when it produces `ScheduleDecision::Switch`. This remains cooperative because the currently executing task polls ticks; no context switch occurs inside IRQ0.

- [ ] **Step 5: Execute decisions after scheduler borrows end**

For each switch, call `prepare_context_switch`, let its `&mut Scheduler` borrow end, then invoke `unsafe { context::switch(&mut *prepared.current, &prepared.next) }`. Give the worker a stable pointer to the scheduler so it can independently wait for the next scheduler decision and switch back.

- [ ] **Step 6: Prove two round trips and then continue to Ring 3**

Expected serial order includes the four `Task switch:` markers followed by the existing syscall-return and Ring 3 breakpoint markers.

- [ ] **Step 7: Run CI and verify GREEN**

Formatting, host tests, check, Clippy, target build, task-switch QEMU smoke, and Ring 3/syscall smoke must all pass.
